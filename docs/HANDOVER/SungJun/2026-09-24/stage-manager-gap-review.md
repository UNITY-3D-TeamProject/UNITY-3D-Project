# StageManager 보완 요소 검토

## 작업 요약
- 현재 `StageManager`와 스테이지 코어 타입을 기준으로 다음 구현에 필요한 요소를 검토했다.

## 방법/접근
- 현재 코드와 기존 스테이지 관리 아키텍처 기록을 비교했다.
- 실제 실행에 필요한 최소 흐름과 이후 확장 항목을 분리했다.

## 변경된 파일
- 런타임 코드 변경 없음
- 본 검토 기록과 `HANDOFF_POINTER.md`만 추가/갱신

## 결정 사항
- 다음 구현의 1순위는 스테이지 순서, 현재 인스턴스/인덱스, 시작, 결과 수신, 종료, 다음 스테이지 진입으로 이어지는 최소 실행 루프다.
- 이벤트는 스테이지 타입 또는 결과를 인자로 전달해야 한다.
- `EStageType`이 앱 종류와 개별 스테이지 식별자를 동시에 담당할 수 있는지는 콘텐츠 목록 확정 후 결정해야 한다.
- 저장, 씬 로딩, 복잡한 상태 머신은 연결 대상 시스템이 확정되기 전까지 분리한다.

## 현재 상태 및 이슈
- `CurrentStage`와 `isSuccess`는 쓰기 경로가 없어 기본값만 반환한다.
- `StageManager`가 `StageBase`의 완료를 전달받을 계약이 없다.
- 스테이지 순서와 현재 스테이지 인스턴스를 보관하지 않는다.
- `EStageType`에는 `None`이 없고 `Turtorial`, `Filepp` 오탈자가 남아 있다.

## 다음 할 일
- 캠페인에서 같은 앱 유형이 여러 번 등장하는지 확인해 `EStageType` 분리 여부를 결정한다.
- 새 intent를 작성한 뒤 최소 실행 루프를 구현하고 첫 스테이지 구현체로 전환을 검증한다.
