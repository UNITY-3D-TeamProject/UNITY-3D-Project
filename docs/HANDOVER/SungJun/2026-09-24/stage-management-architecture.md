# 스테이지 관리 아키텍처 논의

## 작업 요약
- 확정된 스토리와 앱별 플레이 구성을 바탕으로 스테이지 관리 단위를 분석했다.
- 현재 선형 진행에 맞는 ScriptableObject 데이터 주도 구조를 제안했다.

## 방법/접근
- 앱, 캠페인 진행 단계, 실제 게임플레이 방식을 서로 다른 축으로 분리했다.
- 현재는 선형 캠페인 목록으로 단순하게 시작하고, 분기가 실제로 필요할 때 그래프로 확장하도록 범위를 제한했다.

## 변경된 파일
- 런타임 코드 변경 없음
- 본 논의 기록과 `HANDOFF_POINTER.md`만 추가/갱신

## 결정 사항
- `EStageId`: 캠페인 내 개별 스테이지의 고유 식별자
- `EAppType`: Instagram, File, Security, Live 등 어느 앱에서 진행되는지 표현
- `EGameplayType`: Feed, Maze, Combat, Puzzle, Story 등 플레이 방식 표현
- `SOStageData`: 한 스테이지의 설정 데이터
- `SOCampaignData`: 선형 스테이지 순서 목록
- `StageManager`: 시작, 완료 결과 수신, 진행 저장, 다음 스테이지 이동만 조정
- `SStageResult`: 런타임 완료 결과만 전달하며 저장 데이터로 사용하지 않음

## 현재 상태 및 이슈
- 실제 구현은 아직 시작하지 않았다.
- 기획 목록의 `위상정렬`, `숫자퍼즐`, `경도`가 독립 캠페인 스테이지인지 파일 앱 내부 퍼즐인지 확정이 필요하다.
- 보안 앱 전 추가 콘텐츠는 별도 플레이가 없다면 독립 스테이지보다 로비 스토리 비트로 처리하는 편이 적절하다.

## 다음 할 일
- 캠페인 진행표에서 메인 스테이지와 파일 앱 내부 서브 스테이지를 확정한다.
- 확정 후 intent 문서를 작성하고 최소 타입 및 SO 데이터 구조를 구현한다.
