# 스캔 시스템 설계 검토 (2026-10-11)

## 작업 요약 및 방법
- `Core/Scanning`의 9개 스크립트, `Skill/Skills/Scan.cs`, 입력·스킬·피격 호출부와 저장된 시험 씬 구성을 정적으로 검토했다.
- 과설계 여부, 표현의 단순성, 재스캔·복수 콜라이더·반응 소유권과 기존 패턴 활용을 확인했다.
- Unity 실행, 컴파일, 성능 측정은 수행하지 않았다. 아래 조건부 문제는 실행 재현 결과가 아니라 코드 경로에서 확인한 위험이다.

## 결론 및 결정 사항
- 감지(`ScanWave`) → 상태/시간(`ScanTarget`) → 표현/활성화(`ScanReactionBase` 구현)의 분리는 적절하다. 반응 구현이 실제로 3종 있으므로 이 분리 자체를 과설계로 보지 않는다.
- `IScannable`은 구현이 하나지만 감지와 대상의 작은 경계이므로 유지할 만하다. 직접 `ScanTarget`에 의존하는 단순화도 가능하나 우선순위는 낮다.
- 단순 enum 상태를 별도 State 클래스들로 분리하거나 전역 ScanManager, EventBus, Factory, 반응별 인터페이스를 추가할 근거는 현재 부족하다.
- 런타임 변경은 하지 않았다. 아래 권고는 검토 결과이며 구현 결정이 아니다.

## 현재 상태 및 이슈

### 1. 재스캔의 시각적 연속성
- `ScanTarget.BeginScan`은 기존 반응의 `OnScanBegin`을 생략해 튐을 막으려 한다(132~151행).
- 그러나 곧바로 호출되는 `MeshRevealReaction.OnScanUpdate`가 중심·반경을 새 파동 값으로 덮어쓴다(67~72행).
- 이미 드러난 플랫폼에 새 파동이 작은 반경으로 닿으면 다시 일부만 보일 수 있고, 사라지는 중이면 즉시 새 반경으로 복귀한다. 시작 훅 생략만으로 화면 연속성을 보장하지 못한다.
- 재스캔이 단순 유지 시간 연장인지, 새 파동으로 다시 드러내는 동작인지 정한 뒤 작은 분기로 표현할 것을 권장한다. 서로 다른 중심의 반경에 단순 `Max`만 적용하는 것으로는 해결되지 않는다.

### 2. 복수 파동 지원은 현재 불완전함 (조건부)
- `ScanTarget`은 마지막 ScanId 하나만 저장한다(104~138행).
- 두 `ScanWave`가 동시에 같은 대상에 A → B → A → B 순서로 통지하면 매번 새 스캔으로 판단해 종료 시각을 계속 재설정한다. 메시 중심도 번갈아 바뀐다.
- 저장된 시험 구성은 `ScanWave` 하나이며, 한 인스턴스의 `Begin`은 이전 파동을 중단한다. 따라서 현재 단일 파동 사용과 복수 발사체 지원 문제를 구분해야 한다.
- 복수 파동이 요구되지 않으면 단일 파동 계약을 명시하는 정도로 충분하다. 필요할 때만 채택할 파동 우선순위와 최초 접촉 관리 방식을 추가한다.

### 3. 콜라이더 단위 중복 호출
- `ScanWave.Update`는 Overlap 결과의 모든 콜라이더에 대해 `OnScanned`를 호출한다(102~108행).
- 같은 적에 콜라이더가 N개면 `ScanTarget.OnScanned`와 모든 `OnScanUpdate`도 프레임당 N번 실행된다. 캐시는 컴포넌트 조회만 줄이며 반응 호출은 줄이지 않는다.
- 메시 반응은 호출마다 렌더러별 PropertyBlock을 갱신한다.
- 재사용하는 프레임별 대상 집합으로 같은 대상은 한 번만 통지하는 것이 작은 개선이다. 파동 전체에서 한 번만 통지하면 반경 갱신이 끊기므로 구분해야 한다.
- 256개 고정 버퍼의 포화는 이 중복 제거만으로 해결되지 않는다. 현재 시험 씬의 레이어 마스크는 전체 레이어이고, 정식 배치 때 스캔 대상 레이어를 지정할 필요가 있다.

### 4. 반응 자동 탐색의 소유 범위
- `ScanTarget.Awake`는 모든 자식의 반응을 모은다(51~55행). 자식에 별도 `ScanTarget`이 있으면 그 반응까지 부모가 제어한다.
- 그러면 부모 스캔 종료가 자식의 진행 중 반응을 꺼 버리는 등 타이머가 충돌할 수 있다. 현재 시험 배치에서 중첩 구성은 확인되지 않았다.
- 동일 GameObject에 반응을 두는 규칙 + `GetComponents`가 가장 단순한 후보다. 자식 배치가 필요하면 명시 배열이나 가장 가까운 소유 Target 기준으로 제한한다.
- 배열의 빈 항목/파괴된 반응에 대한 검증도 없다. 연결 오류는 초기화 시 명확히 진단하는 편이 좋다.

### 5. 다른 렌더링 효과의 값까지 삭제하는 종료 처리 (조건부)
- `MeshRevealReaction.ApplyProperties`는 기존 PropertyBlock을 읽어 다른 효과의 값을 보존하지만, `OnScanEnd`의 `_shouldHideWhenIdle == false` 경로는 `SetPropertyBlock(null)`로 전체 블록을 지운다(100~104행).
- 동일 렌더러의 피격색·강조 등 다른 효과가 PropertyBlock을 쓰면 함께 사라질 수 있다. 현재 시험 메시들은 hide 옵션이 true이므로 이 경로를 쓰지 않는다.
- 스캔 전용 렌더러를 사용하거나 스캔 값만 원복하도록 책임을 정리할 것을 권장한다. 동시 변경이 있다면 전체 블록 스냅샷 복원도 다른 효과를 덮어쓸 수 있다.

### 6. 표현과 의미를 단순화할 부분
- `ScanWave.Begin`의 `duration`은 확산 시간과 대상 유지 시간을 겸한다. 현재 요구사항과 일치하므로 당장 설정 구조를 추가할 필요는 없지만, 튜닝을 분리할 때 `waveDuration`, `revealDuration`으로 명시한다.
- `size`는 지름이므로 `maxDiameter`가 더 직접적이다.
- `OnScanUpdate`는 매 프레임 일반 갱신이 아니라 파동 접촉 정보 갱신이다. `UpdateWave` 같은 이름이 `OnFade`와 역할을 구분하기 쉽다.
- `OnScanBegin`은 새 ScanId마다 호출되는 것이 아니라 Idle에서 시작할 때만 호출된다. 이 계약을 이름/주석에 드러내는 것이 좋다.
- 반복적인 줄 단위 해설은 줄이고, 중복 호출·재스캔·비활성화 정책처럼 이유와 제약을 남기면 실제 로직을 읽기 쉽다.
- `WeakPoint.cs` 8행의 "배율은 드러남과 무관하게 항상 적용" 주석은 최신 정책과 혼동된다. 약점 콜라이더가 활성인 동안만 실제 피격된다는 조건을 반영해야 한다.
- 약점 반응은 페이드를 사용하지 않지만 `OnScanEnd`까지 활성이다. 현재 기본값에서는 유지 시간에 fade-out 약 1초까지 더해져 약점이 남는다. 정확한 약점 유효 시간을 의도와 대조할 필요가 있다.

### 7. 구현 연결 상태
- `Scan.Execute`는 여전히 로그와 기본 실행 통지만 한다. `_Project` 코드에서 `ScanWave.Begin` 호출을 찾지 못했고, 시험 호출은 Git 제외 `Assets/Test/.../ScanTestTrigger.cs`에 있다.
- 스캔 컴포넌트의 저장된 씬/프리팹 참조는 조사 범위에서 `Assets/Test/.../TempScene.unity`에만 있다.
- `WeakPoint.GetMultiplier`의 실제 피해 경로 호출이 없다. 약점 오브젝트 표시/활성화와 약점 피해 배율 완성은 별개다.
- 위 두 연결 작업은 기존 인수인계에도 남아 있는 후속 사항이다.
