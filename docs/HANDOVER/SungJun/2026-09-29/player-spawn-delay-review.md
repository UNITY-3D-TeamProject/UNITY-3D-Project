# 플레이어 지연 스폰 필요성 검토

- 작업 요약 및 방법: PlayerSpawner, GameManager, Singleton, PlayerState, AttributeSet, UIManager와 StageManager의 초기화·생성·등록 흐름을 확인하고 Unity 공식 실행 순서 문서를 대조했다. 런타임 코드는 수정하지 않았다.
- 결정 사항: 활성 GameManager가 씬에 배치되고 필요한 SO가 연결되어 있다는 전제에서 현재 Start의 즉시 스폰을 유지할 수 있다. GameManager의 PlayerState는 Awake에서 생성되고, 활성 플레이어 프리팹의 AttributeSet은 Instantiate 중 Awake에서 초기화되므로 추가 시간 지연은 필요하지 않다. UI는 생성 이벤트와 현재 플레이어 조회로 연결한다.
- 현재 상태 및 이슈: 초기화 실패나 참조 누락은 임의 시간 지연으로 해결되지 않는다. 사망 연출·재시작 카운트다운은 기획에 따라 대기할 수 있으며, 향후 비동기 준비 과정이 생기면 완료 조건을 기다려야 한다. Unity 플레이 실행은 하지 않았으며 사망 처리 연결 여부를 변경하지 않았다.
- 다음 할 일: 지연 스폰 구현 요청 없음. 사망 재스폰을 연결할 때 연출 대기 필요 여부와 기존 플레이어 제거·등록 순서를 확인한다.

## 외부 데이터 주입과 비활성 생성 후속 확인

- 활성 프리팹의 Instantiate는 Player의 Awake 및 활성 컴포넌트의 OnEnable을 실행한 뒤 반환하므로 이후 주입한 값을 이 콜백에서 미리 사용할 수 없다.
- 처음부터 GameObject가 비활성인 프리팹을 생성하면 Awake도 최초 활성화까지 미뤄진다. 컴포넌트 enabled=false만으로는 Awake가 미뤄지지 않는다. Unity의 Awake 및 Instantiate 공식 문서로 확인했다.
- Awake에 외부 주입 데이터 의존 로직을 두지 않는 것은 활성 생성 후 주입 방식에 적합한 설계 원칙이다. 모든 프리팹을 항상 비활성으로 관리해야 한다는 필수 규칙은 아니다. 명시적 Initialize 호출로 외부 데이터 설정과 그 데이터에 의존하는 초기화를 함께 수행할 수 있다.
- 현재 프로젝트의 AttributeSet은 Awake에서 딕셔너리를 구성하므로 비활성 생성 직후 RegisterPlayer로 능력치를 복원하는 흐름으로 단순 변경하면 초기화 전 복원 시도가 된다. 스폰 지연 시간보다 초기화·복원·사용 순서를 판단해야 한다.

## 능력치 딕셔너리 소유 위치 후속 설명

- 현재 플레이어 인스턴스에 붙은 AttributeSet이 private 필드 _attributes로 실제 능력치 딕셔너리를 소유한다. Player 클래스에 별도 딕셔너리를 추가할 필요는 없다.
- SOAttributeData는 초기값 원본이며 PlayerState의 별도 딕셔너리는 씬 전환 시 보관할 능력치 값의 사본이다.
- _attributes 객체 생성은 필드 초기화에서 수행하고 SO 항목을 넣는 작업은 Awake에서 수행한다. 소유 위치와 초기화 완료 시점은 별개의 판단 사항이며, 이번 대화에서 런타임 코드 변경은 하지 않았다.

## 스포너에서 초기값 설정 후 활성화하는 방향 확인

- 사용자는 Awake에서 능력치 초기값을 채우지 않고 PlayerSpawner에서 채운 다음 활성화하는 구조를 의도한다고 명확히 했다. 해당 구조는 처음부터 비활성인 플레이어 프리팹을 Instantiate하여 초기화 후 SetActive(true)로 활성화하는 방식으로 구성할 수 있다고 답변했다.
- 활성화 시 실행되는 Awake에서 주입값을 덮어쓰지 않아야 한다. 현재 AttributeSet의 SetValue는 기존 항목 수정 함수이므로 빈 딕셔너리를 채우는 초기화 함수가 필요하다. 스포너가 그 함수를 호출하고 실제 딕셔너리는 계속 플레이어의 AttributeSet이 소유한다.
- 이번 요청은 방식의 적합성 확인이며 런타임 코드 구현은 요청되지 않았다.

## 비활성 프리팹 저장의 필수 여부 확인

- 프리팹 에셋 자체를 비활성으로 저장할 필요는 없다. 활성 프리팹도 비활성 부모 Transform을 Instantiate에 전달하면 생성 시 activeInHierarchy=false가 되어 Awake/OnEnable 전에 데이터를 설정할 수 있다. 설정 완료 후 활성 계층으로 옮겨 활성화할 수 있다.
- Awake/OnEnable에서 외부 주입값을 사용하지 않고 명시적 초기화 이후에 사용하도록 구성하면 활성 생성 후 초기화도 가능하다.
- Awake/OnEnable이 주입된 값을 사용해야 한다면 최초 활성화 전에 설정을 완료해야 한다. 활성 Instantiate 이후 SetActive(false)를 호출하는 것은 이미 실행된 Awake/OnEnable을 막지 못한다. 이번에도 런타임 코드는 변경하지 않았다.

## Instantiate의 비활성 지정 옵션 확인

- 사용자는 Instantiate 호출 자체에 생성 객체의 활성 상태를 지정하는 옵션이 있는지 확인했다. 해당 옵션은 없으며, 비활성 부모를 전달하는 방식은 부모의 계층 상태를 이용하는 것이라고 명확히 답변했다. 원본 프리팹의 활성 상태는 복제되고, 활성 계층에서 생성한 뒤 SetActive(false)를 호출해도 최초 Awake/OnEnable을 막지 못한다.
