# Codex 인수인계 — 플레이어 스폰·체크포인트·낙하·사망 복구

작성일: 2026-10-08 (Asia/Seoul)

후속 상태 (2026-10-08): 이 문서 최초 작성 뒤 사용자가 1단계 StageManager 데이터 코드를 적용했다. 라운드 체크포인트 인덱스 배열, 현재 라운드 인덱스 및 진행도 조회 프로퍼티가 추가됐다. 초기 작성 시점의 아래 기록과 구분해서 읽을 것. Unity 검증과 2~9단계 기능 구현은 아직 하지 않았다. 코드와 문서는 별도 커밋으로 원격 반영을 요청받았으며, 동기화 여부는 현재 Git 이력을 확인한다.

이 문서는 다른 로컬 환경의 Codex가 이전 대화 없이 작업을 이어갈 수 있도록 정리한 단일 인수인계 파일이다. 아래 경로는 모두 저장소 루트 기준이다. 이 파일만 전달해도 설계와 구현 순서를 이해할 수 있다.

## 1. 현재 상태와 작업 범위

- 지금까지 진행한 것은 Core 코드 검토, 설계, 구현 순서 합의다.
- 이 대화에서 게임 스크립트, 씬, 프리팹은 수정하지 않았다. 설계·인수인계 문서와 목차만 작성했다.
- 기능 구현, Unity 컴파일, Play Mode 검증, 성능 측정은 아직 하지 않았다.
- 사용자는 Core 폴더의 스크립트를 본인이 작성했으므로 그 코드를 기준으로 설명하고 설계해 달라고 요청했다.
- Core 밖 전투·이동 시스템의 내부 구현은 이번 검토에서 읽지 않았다. 기존 사망/부활/이동 API를 확인했다고 가정하지 말 것.
- 최신 합의는 이 문서를 기준으로 한다. 초기 설계에서 대안으로 언급한 사망 시 삭제/재생성보다, 기존 플레이어 재사용을 채택한 후속 합의가 우선한다.
- 이 문서를 읽는 것만으로 구현 시작을 요청받았다고 해석하지 않는다. 다음 사용자 요청의 범위에 맞춰 진행한다.

5. 구현을 요청받으면 구현 범위의 intent를 확인/등록한다. 기존 intent-015의 완료는 설계 완료를 의미하며 기능 구현 완료가 아니다.

## 3. 사용자와 확정한 동작

### 최초 스폰

- 플레이어를 어디에 생성할지는 StageManager가 결정한다.
- PlayerSpawner는 전달받은 위치에 플레이어를 생성한다.
- 기존 로비/스테이지 분기를 유지한다. 로비는 기존 복귀 위치 선택을 사용하고, 스테이지는 StageManager에서 위치를 받는다.
- 같은 씬의 사망에서는 플레이어를 삭제하고 다시 만들지 않는다. 기존 플레이어를 이동하고 상태를 복구한다.
- 씬 전환으로 플레이어가 파괴되면 새 씬에서 생성할 수 있다. 게임 전체에서 단 한 번 생성하거나 DontDestroyOnLoad로 영구 유지하기로 정한 것은 아니다.

### 낙하 후 생존

- 플랫폼 아래 낙하 구역으로 떨어지면 낙하 데미지를 한 번 적용한다.
- 데미지 적용 후 HP > 0이면 살아 있는 상태다.
- 실제 도달한 모든 체크포인트 중 가장 높은 인덱스로 이동한다. 라운드 체크포인트도 이 목록에 포함된다.
- 방문하지 않은 높은 인덱스 지점으로 이동하면 안 된다.
- 체력은 데미지 적용 후 값, 배터리는 현재값을 유지한다. 라운드 스냅샷을 복원하지 않는다.

### 원인과 관계없는 사망

- HP <= 0이면 원인과 관계없이 사망으로 판정한다.
- 현재 라운드에 지정된 체크포인트로 이동한다.
- 그 라운드 체크포인트를 최초로 찍었을 때의 체력과 배터리를 복원한다.
- 재접촉하거나 반복 사망해도 최초 저장값을 덮어쓰지 않는다.
- 일반 체크포인트 진행도도 해당 라운드 시작점으로 되돌린다. 이 항목은 사용자가 별도 질문에 직접 확인한 사항이다.
- 위치와 두 능력치 외에, 실제 사망 처리에서 바뀐 사망 플래그·이동 상태·입력 등을 정상 플레이 가능하게 복구해야 한다.

예: 라운드 시작 C0 → C1 → C2까지 진행한 경우, 생존 낙하는 C2로 복귀한다. 완전 사망은 C0으로 복귀하며 최신 체크포인트도 C0이 된다. C1을 다시 찍기 전 낙하하면 C0으로 돌아간다.

## 4. 책임 분리

| 구성 요소 | 책임 |
|---|---|
| StageManager | 체크포인트/라운드 설정과 진행도, 목적지 결정, 기존 플레이어 이동, 낙하와 사망 복구 순서 조율 |
| PlayerSpawner | 위치를 전달받아 생성, 초기화, 생성 완료 통지. 같은 씬의 사망 복구에서는 호출하지 않음 |
| PlayerState | 현재 AttributeSet 참조, 씬 전환용 저장, 별도의 라운드 최초 HP·배터리 스냅샷 저장·복원 |
| GameManager | PlayerState 소유와 수명, 씬 전환 및 플레이어 등록 흐름 연결 |
| 기존 전투/능력치 시스템 | 공통 사망 판정·통지와 부활 상태 초기화 계약. 실제 담당 API는 구현 전 확인 필요 |
| 기존 이동 시스템 | StageManager의 이동 요청에 따른 위치·속도·낙하 상태 초기화 계약. 실제 API는 구현 전 확인 필요 |

사용자가 언급한 gameState는 데이터 저장 의도였다. 현재 코드의 `GameManager.GameState`는 Title / Playing / Pause enum이므로 저장소로 확장하지 않는다. 기존 `GameManager.playerState`의 `PlayerState`를 활용한다.

StageManager가 복구를 조율하되 전투·이동 컴포넌트의 내부 필드를 여기저기 직접 수정하는 구조는 피한다. 각 담당 컴포넌트의 명시적인 초기화 기능을 호출하는 방향이다.

## 6. 데이터·패턴 제안

아래 이름과 구조는 제안이며 이미 구현된 API가 아니다.

```text
StageManager
  전체 체크포인트 목록: SCheckpoint[]
  라운드별 시작점 매핑: 라운드 번호 → 공통 체크포인트 인덱스
  현재 라운드
  최근 체크포인트 인덱스
  복구 처리 상태

PlayerState
  기존 씬 전환용 Attribute 저장 공간
  별도의 라운드별 SRoundCheckpointSnapshot 저장 공간

SRoundCheckpointSnapshot
  CheckpointIndex
  Health
  Battery
```

- Memento의 스냅샷 방식을 적용한다. AttributeSet 참조가 아니라 최초 HP·배터리의 값을 복사한다.
- 씬 전환용 저장과 라운드 저장을 분리한다. 전체 Attribute 복원으로 버프·공격력 등까지 되돌리지 않는다.
- 기존 OnPlayerSpawned/OnDeath 이벤트에는 Observer 구조를 활용한다.
- 작은 enum 상태로 정상 플레이/낙하 복귀/사망 복구를 구분해도 충분하다.
- 지금은 Strategy 계층, 상태 클래스 계층, 플레이어용 오브젝트 풀을 추가할 필요가 없다.
- 새 스테이지 시도에서는 라운드 스냅샷을 초기화하고, 같은 시도의 사망 재시도에서는 유지하는 것을 기본안으로 제안했다. 씬 재로드/이어하기 수명 정책이 추가되면 별도로 정한다.
- 런타임 메모리 저장이 범위다. 게임 종료 후 디스크 저장·이어하기는 요청되지 않았다.

같은 플레이어 재사용은 일반적으로 생성/삭제보다 할당과 생성 처리 부담이 적고 기존 참조를 유지하기 쉽다. 실제 성능 차이는 측정하지 않았으며 낮은 사망 빈도에서 큰 차이가 난다고 단정하지 않는다.

## 7. 최종 구현 순서 — 반드시 사망 판정을 독립 단계로 포함

사용자가 사망 판정도 별도 번호로 넣어야 한다고 지적했고, 아래 순서로 수정했다. 예전 문서의 낙하 우선 순서보다 이 순서가 최신이다.

1. **체크포인트 데이터 구성**
   - StageManager에 공통 체크포인트 목록과 라운드별 시작점 매핑 구성.
   - 현재 라운드와 최근 체크포인트 인덱스 분리.

2. **PlayerState의 라운드 최초 체력·배터리 저장·복원**
   - 씬 전환용 저장과 분리.
   - 동일 라운드 최초 저장값을 재시도 중 덮어쓰지 않기.

3. **StageManager → PlayerSpawner 최초 스폰 위치 전달**
   - StageManager가 위치 결정, PlayerSpawner가 한 번 생성.
   - 최종 초기 능력치 적용 후 첫 라운드 스냅샷 준비.

4. **체크포인트 도달·라운드 최초 스냅샷 저장 처리**
   - 실제 도달한 높은 인덱스로 일반 진행도 갱신.
   - 라운드 시작점 최초 도달 시 스냅샷 저장.

5. **기존 플레이어 이동·이동 상태 초기화**
   - StageManager의 공통 이동 함수와 기존 이동 시스템 연결.
   - 이동 시 남은 낙하 속도·외력 등 정리.

6. **플레이어 사망 판정 및 이벤트 연결**
   - 기존 전투/능력치 공통 경로에서 HP <= 0 사망 판정 확인 및 필요한 연결.
   - 살아 있음 → 사망 전이에서 한 번만 통지.
   - StageManager가 사망 통지를 받기.
   - 이미 있는 판정과 중복되는 별도 판정 시스템을 무조건 추가하지 않기.

7. **사망 후 라운드 복구**
   - 현재 EndStage 기반 처리를 라운드 복구로 변경.
   - 라운드 시작점 이동, 일반 체크포인트 진행도 되돌리기, 최초 HP·배터리 복원.
   - 사망 상태를 해제하여 다음 사망도 다시 판정할 수 있게 처리.
   - 플레이어를 삭제하거나 다시 생성하지 않기.

8. **낙하 데미지와 생존 복귀**
   - 낙하 감지와 데미지 1회 적용.
   - 생존하면 최근 체크포인트로 이동.
   - 사망하면 6~7번 공통 흐름 사용.

9. **중복 처리 방지와 통합 검증**
   - 낙하와 사망이 겹쳐도 복구 한 번만 실행.
   - 최초 입장 직후 사망, 반복 사망, 생존 낙하, 다음 라운드 진입 확인.
   - 중복 방지 장치는 6~8번 구현 시 함께 넣고, 마지막에 통합 검증한다.

## 8. 구현 시 반드시 지킬 실행 순서

### 초기 준비

- 첫 체크포인트에 접촉하기 전에 사망하더라도 복구 가능해야 한다.
- 초기 스폰의 능력치 초기화/씬 전환 복원이 끝난 뒤 첫 라운드 스냅샷을 저장한다.
- StageManager의 설정 준비와 실제 플레이 시작을 구분한다. 현재 sceneLoaded에서 StartStage를 호출하므로 플레이어 생성·스냅샷보다 진행이 앞서지 않는지 확인한다.
- 최초 생성을 StageManager와 PlayerSpawner 양쪽에서 중복 호출하지 않는다.

### 사망과 낙하의 중첩

- 낙하 데미지 적용 중 동기적으로 OnDeath가 호출될 수 있다.
- 사망 콜백이 즉시 HP 복원까지 끝내면 낙하 함수가 복원된 HP를 보고 생존으로 판단하여 두 번째 이동을 실행할 수 있다.
- 사망 요청을 먼저 확정/보존하고, 데미지 처리 뒤 복귀 경로 하나만 실행한다.
- 사망 판정이 확정된 요청은 복원된 HP 때문에 생존 낙하 경로로 바뀌면 안 된다.
- 반복 트리거와 복수 Collider로 중복 데미지/복구가 발생하지 않도록 한다.

### 복구

- 복구 중 입력·추가 피격·체크포인트 갱신을 제한한다.
- 실제 플레이어 이동 대상과 이동 상태 초기화 계약을 사용한다. AttributeSet이 붙은 자식만 이동하지 않는다.
- 사망 시 일반 체크포인트 인덱스뿐 아니라 관련 활성화 표시/캐시도 라운드 시작점에 맞춘다.
- HP·배터리와 함께 실제 변경된 사망 플래그·애니메이션·입력·충돌 상태를 복구한다.
- 같은 객체를 이동하는 경우 CompletePlayerSpawn을 재호출해 기본 스폰 초기화/저장을 건드리지 않는다.
- 라운드 재시도는 스테이지 최종 실패와 구분한다. EndStage로 현재 StageBase 참조를 비워버리지 않는다.

## 9. 구현 전 확인이 필요한 항목

설계는 합의됐지만 아래 사실은 아직 검증하지 않았다. 구현에 필요한 항목을 실제 코드/데이터에서 확인하고, 요구사항 선택이 필요하면 사용자에게 묻는다.

- 실제 HP/배터리 Attribute 키와 값 변경 API.
- 모든 HP 감소 원인이 공통 사망 통지로 연결되는지.
- 기존 사망 처리가 플레이어를 파괴하거나 컴포넌트를 비활성화하는지, 재사용을 위한 부활 API가 있는지.
- 실제 이동 대상과 워프, 속도·외력 초기화 API.
- 라운드가 체크포인트 도달로 전환되는지, 별도 목표 완료로 전환되는지. StageProgress를 임의로 라운드 번호로 해석하지 않는다.
- 라운드 재시도 시 적·기믹·목표 진행까지 초기화할지. 확정 범위는 플레이어 복구이며 월드 전체 롤백은 미정이다.

## 10. 완료 검증 기준

- 생존 낙하: 데미지를 한 번 받고 최근 활성 체크포인트로 이동, 현재 HP·배터리 유지.
- 치명적 낙하: 일반 복귀가 추가 실행되지 않고 라운드 복구 한 번만 수행.
- 전투 등 다른 원인의 사망: 동일한 공통 복구 실행.
- 반복 사망/체크포인트 재접촉: 최초 라운드 HP·배터리 불변.
- 사망 후 일반 체크포인트 진행도 초기화, 이후 재진행 가능.
- 첫 스폰 직후 사망: 올바른 시작점과 초기 스냅샷 사용.
- 부활 후 두 번째 사망도 정상 판정.
- 복구 뒤 낙하 속도, 사망 플래그, 입력 잠금 등이 남지 않음.
- 같은 씬 사망 복구에서 플레이어 재생성이나 플레이어 중복 없음.
- 로비 스폰 및 기존 씬 전환 저장·복원 유지.
