# 스마트폰 속 세계로 (Unity 3D 게임 프로젝트)

스마트폰 속 디지털 공간을 탐험하는 **3D 플랫포머 + TPS** 프로젝트이다.  
GitHub의 Issue / Branch / Pull Request를 기준으로 협업하며, 모든 작업은 기록과 리뷰를 원칙으로 한다.

---

## 프로젝트 정보

| 항목 | 내용 |
|---|---|
| 프로젝트명 | 스마트폰 속 세계로 |
| Engine | Unity 6000.4.8f1 |
| Render Pipeline | URP (또는 3D Built-in) |
| Version Control | GitHub |
| 장르 | 3D 플랫포머 + TPS |
| 플랫폼 | PC |

> Unity 버전과 Render Pipeline은 팀 전체가 동일하게 유지한다. 실제 프로젝트 설정에 맞추어 Render Pipeline을 최종 확정한다.

---

## 팀원 및 역할

- **양준범** : 맵 / 레벨
- **이세훈** : 플레이어 / 전투
- **이정빈** : 적 / NPC AI
- **김성준** : 시스템 / UI / 연출

역할 변경 시 README와 관련 Issue / PR의 담당자를 함께 수정한다.

## 게임 소개

### 콘셉트

스마트폰 내부의 디지털 세계를 탐험하며 다양한 이동 수단과 전투 요소를 활용하는 3D 어드벤처 게임이다.

### 핵심 플레이

- 스마트폰 속 앱 세계 탐험
- 와이파이 포탈을 통한 공간 이동
- 블루투스 행글라이더를 활용한 이동
- 데이터 패킷을 활용한 전투
- SNS 및 디지털 공간을 활용한 진행

### 스토리

K-POP 가수를 꿈꾸는 폰 주인의 잠긴 노래 파일을 해제하고, 이를 SNS에 업로드하여 유명 아티스트로 만들어 가는 이야기이다.

## 1. 프로젝트 세팅

### 필수 환경

1. Unity Hub에서 **Unity 6000.4.8f1** 설치
2. Git 설치
3. GitHub 저장소 Clone
4. Unity Hub에서 Clone한 프로젝트 실행
5. Package Manager와 Project Settings가 팀 기준과 일치하는지 확인

### 최초 실행 후 확인 사항

- Unity 버전 일치 여부
- Render Pipeline 일치 여부
- Console Error 발생 여부
- 담당 씬 / 프리팹 정상 실행 여부
- 불필요한 Git 변경 사항 생성 여부

> `Library/`, `Temp/`, `Logs/` 등 Unity가 자동 생성하는 폴더는 `.gitignore`로 관리한다.

## 2. GitHub 협업 규칙

### 2-1. 기본 작업 순서

```text
Issue 확인 / 생성
        ↓
작업 브랜치 생성
        ↓
최신 develop 반영
        ↓
기능 / 버그 작업
        ↓
Unity 테스트
        ↓
Commit
        ↓
Push
        ↓
Pull Request 생성
        ↓
리뷰 및 수정
        ↓
develop Merge
        ↓
release 시점에 main 반영
```

`main`과 `develop`에는 직접 Push하지 않는다. 작업 브랜치에서 작업 후 PR을 통해 병합한다.

### 2-2. 브랜치 규칙

브랜치 이름은 다음 형식을 사용한다.

```text
feature/<issue-number>-<short-description>
bugfix/<issue-number>-<short-description>
refactor/<issue-number>-<short-description>
chore/<issue-number>-<short-description>
```

예시:

```text
feature/12-player-movement
bugfix/18-camera-limit
refactor/21-enemy-fsm
chore/25-readme-update
```

#### 작성 규칙

- 작업 목적을 명확하게 작성한다.
- 가능하면 Issue 번호를 포함한다.
- 띄어쓰기 대신 `-`를 사용한다.
- 하나의 브랜치에는 하나의 작업만 포함한다.

### 2-3. 커밋 메시지 컨벤션

#### 구조

```text
태그: 요약문
- 작업자
- 상세 작업 내용 1 (선택)
- 상세 작업 내용 2 (선택)
```

#### 태그

모든 태그는 소문자로 작성하며 콜론 뒤에 한 칸을 둔다.

| 태그 | 용도 | 예시 |
|---|---|---|
| `feat` | 기능 / 시스템 / 스크립트 / 에셋 추가 | `feat: 플레이어 이동 및 점프 기능 구현` |
| `fix` | 버그 / 에러 / 씬 / 프리팹 문제 수정 | `fix: 카메라 경계 이탈 오류 수정` |
| `refactor` | 기능 변화 없이 구조 개선 / 최적화 | `refactor: 전투 상태 전환 구조 개선` |
| `chore` | 폴더 / 패키지 / Git / 문서 작업 | `chore: GitHub Issue Template 추가` |

#### 작성 규칙

`~함`, `~했음` 대신 `~구현`, `~수정`, `~제거`, `~추가` 형태를 사용한다.

권장:

```text
feat: 인벤토리 슬롯 드래그 앤 드롭 구현
fix: 플레이어 낙하 시 콜라이더 끼임 현상 제거
chore: README에 브랜치 전략 추가
```

지양:

```text
feat: 인벤토리 슬롯 드래그 앤 드롭 구현함
fix: 버그 고쳤음
```

#### Commit 원칙

- 하나의 Commit에는 하나의 논리적 변경만 포함한다.
- 테스트하지 않은 기능을 정상 동작으로 기록하지 않는다.
- 변경 내용을 확인할 수 있도록 작성한다.
- Unity가 자동 생성하는 불필요한 파일은 Commit하지 않는다.

### 2-4. 씬 / 프리팹 작업 규칙

**공용 Base Scene은 담당자 승인 없이 수정하지 않는다.**

- 공용 씬의 대규모 수정은 PR에 변경 내용을 기록한다.
- 공용 프리팹 수정 시 영향 범위를 PR에 기록한다.
- 동일한 씬에서 동시에 대규모 작업을 진행하지 않는다.
- 신규 기능은 가능하면 테스트 씬 또는 별도 프리팹으로 검증한 후 통합한다.

## 3. GitHub Issue Template 사용법

Issue Template은 작업 요구사항과 문제 상황을 기록하는 용도로 사용한다.

현재 사용 템플릿:

```text
.github/
└── ISSUE_TEMPLATE/
    ├── feature_request.md
    └── bug_report.md
```

GitHub에서 `New issue`를 선택한 후 목적에 맞는 Template을 선택한다.

### 3-1. 기능 제안

`feature_request.md`는 새로운 기능이나 시스템을 제안할 때 사용한다.

#### 사용 시점

- 신규 플레이 기능 추가
- 신규 UI / 연출 추가
- 기존 시스템 확장
- 편의성 또는 게임성 개선

#### 작성 항목

1. **제안하는 기능** : 추가할 기능을 작성한다.
2. **제안 배경** : 필요한 이유를 작성한다.
3. **게임 내 동작** : 플레이어 관점에서 실제 동작 과정을 순서대로 작성한다.
4. **세부 내용** : 입력, 동작 조건, 결과, 관련 시스템, 예외 상황 등을 작성한다.

예시:

```text
제안하는 기능
- 플레이어가 공중에서 블루투스 행글라이더를 소환하여 활강할 수 있도록 구현

제안 배경
- 높은 플랫폼 사이의 이동 수단이 필요함

게임 내 동작
1. 공중에서 지정 키 입력
2. 행글라이더 소환
3. 플레이어 활강 시작

세부 내용
- 입력: 지정 키
- 동작 조건: 공중 상태
- 결과: 활강 상태 전환
- 관련 시스템: 플레이어 이동 / 애니메이션
- 예외 상황: 지형 충돌 시 활강 종료
```

### 3-2. 버그 리포트

`bug_report.md`는 플레이 중 발생한 버그, 에러, 씬 / 프리팹 이상을 기록할 때 사용한다.

#### 작성 항목

1. **버그 설명** : 실제 문제를 작성한다.
2. **재현 방법** : 발생 과정을 순서대로 작성한다.
3. **실제 결과** : 현재 발생하는 결과를 작성한다.
4. **기대 결과** : 정상적으로 동작해야 하는 결과를 작성한다.
5. **발생 환경** : Unity 버전, OS, 씬, 발생 빈도, 재현 가능 여부를 작성한다.
6. **확인 사항** : 최신 `develop` 재현 여부, Console Error / Warning, Missing Reference, 재현 절차를 확인한다.

예시:

```text
버그 설명
- 플레이어가 경사면에서 점프 후 바닥 아래로 이동함

재현 방법
1. TestStage 씬 실행
2. 시작 지점 오른쪽 경사면으로 이동
3. 점프
4. 착지 직후 플레이어 위치 확인

실제 결과
- 플레이어 Y좌표가 바닥 아래로 내려감

기대 결과
- 경사면 위에 정상적으로 착지함

발생 환경
- Unity: 6000.4.8f1
- OS: Windows 11
- Scene: TestStage
- 발생 빈도: 항상
- 재현 가능 여부: 재현 가능
```

## 4. Pull Request Template 사용법

PR은 작업 결과를 리뷰받고 브랜치를 병합하기 위한 문서이다.

템플릿 위치:

```text
.github/
└── PULL_REQUEST_TEMPLATE.md
```

작업 브랜치를 Push한 뒤 GitHub에서 `Create pull request`를 선택하면 템플릿이 표시된다.

### PR 작성 항목

#### 1. 작업 종류

해당 항목을 체크한다.

- 새로운 기능 추가
- 버그 수정
- 리팩토링
- 기획 / 문서 수정

#### 2. 작업 내용

실제 변경 사항을 작성한다.

```text
- PlayerController 이동 로직 구현
- Ground Check 추가
- 이동 / 점프 애니메이터 파라미터 연결
```

#### 3. 씬 / 프리팹 변경 사항

변경된 Scene, Prefab, GameObject와 주의할 참조 관계를 작성한다.

```text
- 변경된 Scene: MainScene
- 변경된 Prefab: Player
- 추가 / 삭제된 GameObject: GroundCheck
- 주의할 참조 관계: PlayerController의 Animator 참조
```

#### 4. 에셋 변경 사항

에셋 추가 여부를 체크한다. 신규 에셋이 있는 경우 다음 정보를 작성한다.

```text
- 에셋명:
- 제작자:
- 출처(URL):
- 라이선스:
- 크레딧 필요 여부:
- 에셋 공유 여부:
```

에셋 정보는 README의 에셋 / 라이선스 관리 기준에 맞춰 작성한다.

#### 5. 주요 변경 파일

이번 PR에서 주요하게 수정하거나 추가한 파일의 경로를 작성한다.

```text
- Assets/Scripts/Player/PlayerController.cs
- Assets/Prefabs/Player.prefab
- Assets/Scenes/MainScene.unity
```

#### 6. 테스트

실제로 확인한 테스트 내용을 작성한다.

권장 확인 항목:

```text
- [ ] Unity Editor에서 정상 동작 확인
- [ ] Console Error / Warning 확인
- [ ] 관련 Scene 실행 확인
- [ ] 관련 Prefab 동작 확인
- [ ] 기존 기능 정상 동작 확인
```

테스트 체크 항목과 함께 실제 수행한 내용을 작성한다.

```text
- 플레이어 이동 확인
- 점프 및 착지 확인
- Scene 재실행 확인
```

#### 7. 주의 사항 / 리뷰 포인트

리뷰어가 확인해야 하는 변경 사항이나 주의점을 작성한다.

```text
- PlayerController 구조 변경
- 기존 전투 입력과 충돌 여부 확인
- MainScene의 Player Prefab 참조 확인
```

#### 8. 스크린샷 / 영상

변경 결과를 확인할 수 있는 스크린샷이나 영상을 필요한 경우 첨부한다.

#### 9. 관련 Issue

관련 Issue를 연결한다.

```text
Closes #12
```

Issue 번호를 연결하면 PR 병합 시 관련 Issue가 자동으로 종료된다.

## 5. 리뷰 및 Merge 규칙

- PR은 다른 팀원의 리뷰 후 Merge한다.
- 기능 구현은 실제 플레이 테스트 여부를 확인한다.
- 씬 / 프리팹 수정은 참조 누락 여부를 확인한다.
- 공용 시스템 수정은 영향 범위를 확인한다.
- 충돌 해결 후 Unity 재테스트를 수행한다.
- Merge 후 관련 씬을 실행하여 최종 확인한다.

### 리뷰 체크리스트

```text
[ ] 요구사항대로 동작하는가?
[ ] 기존 기능이 깨지지 않았는가?
[ ] Null Reference / Missing Reference가 없는가?
[ ] 씬 / 프리팹 참조가 끊기지 않았는가?
[ ] 불필요한 Debug.Log 또는 테스트 코드가 남아 있지 않은가?
[ ] 다른 담당자의 코드와 충돌 가능성이 없는가?
```

## 7. 3D Unity 작업 규칙

3D 프로젝트는 씬, 프리팹, Material, Animator, Particle, Collider 등의 연결 관계가 많으므로 에디터 상태와 실제 플레이 결과를 함께 확인한다.

### 작업 시 확인 사항

- Script 변경 후 해당 Script가 사용되는 Prefab 확인
- Prefab 변경 후 배치된 Scene 확인
- Material / Shader 변경 후 조명과 카메라 확인
- Collider / Rigidbody / CharacterController 변경 후 실제 충돌 확인
- Animator 변경 후 전이 조건과 파라미터 확인
- Particle / VFX 변경 후 Game View에서 확인
- 신규 에셋 추가 시 라이선스와 크레딧 기록

### 테스트 씬

신규 시스템은 메인 씬에 바로 적용하기보다 테스트 씬에서 먼저 검증한다.

```text
TestScene
 ├─ Player
 ├─ System Test Area
 ├─ Required UI
 └─ Debug Objects
```

테스트 완료 후 통합 씬에 적용하고 PR에 반영 위치를 기록한다.

## 8. 에셋 / 라이선스 크레딧

프로젝트에서 사용하는 외부 에셋은 제작자, 출처, URL, 라이선스, 사용 조건을 기록한다.

### 에셋 등록 템플릿

| 항목 | 내용 |
|---|---|
| 에셋명 | |
| 제작자 | |
| 출처 | |
| URL | |
| 라이선스 | |
| 상업적 사용 | 가능 / 불가 / 확인 필요 |
| 수정 가능 | 가능 / 불가 / 확인 필요 |
| 크레딧 필요 | 필요 / 불필요 / 확인 필요 |
| 비고 | |

### 에셋 추가 절차

```text
에셋 다운로드
    ↓
라이선스 확인
    ↓
README 에셋 목록 등록
    ↓
Unity 프로젝트에 추가
    ↓
사용 위치 확인
    ↓
PR에 출처 / 라이선스 기록
```

라이선스를 확인하지 못한 에셋은 상업적 사용 가능으로 판단하지 않는다. 라이선스가 명시되지 않은 경우 사용 전에 제작자에게 확인한다.

## 9. 작업 전 체크리스트

### 작업 시작 전

```text
[ ] 관련 Issue가 있는가?
[ ] 최신 develop을 Pull 했는가?
[ ] 올바른 작업 브랜치를 생성했는가?
[ ] 수정할 Scene / Prefab이 다른 작업과 겹치지 않는가?
```

### 작업 완료 전

```text
[ ] Unity에서 직접 테스트했는가?
[ ] Console Error / Warning을 확인했는가?
[ ] Scene / Prefab 참조가 깨지지 않았는가?
[ ] 불필요한 테스트 코드 / 로그를 제거했는가?
[ ] Commit 메시지가 규칙에 맞는가?
[ ] 신규 에셋의 라이선스 정보를 등록했는가?
```

### PR 생성 전

```text
[ ] PR 템플릿의 작업 종류를 체크했는가?
[ ] 작업 내용을 작성했는가?
[ ] Scene / Prefab 변경 사항을 작성했는가?
[ ] 에셋 변경 사항을 작성했는가?
[ ] 주요 변경 파일을 작성했는가?
[ ] 테스트 내용을 작성했는가?
[ ] 리뷰 포인트 / 주의 사항을 작성했는가?
[ ] 관련 Issue를 연결했는가?
[ ] 필요한 스크린샷 / 영상을 첨부했는가?
```

## 10. GitHub 템플릿 파일 구조

```text
.github/
├── ISSUE_TEMPLATE/
│   ├── feature_request.md
│   └── bug_report.md
└── PULL_REQUEST_TEMPLATE.md
```

### 템플릿 사용 시점

| 파일 | 사용 시점 | 핵심 목적 |
|---|---|---|
| `feature_request.md` | 새로운 기능 제안 | 기능의 필요성, 게임 내 동작, 구현 세부 내용 기록 |
| `bug_report.md` | 버그 / 에러 제보 | 문제 설명, 재현 방법, 실제 / 기대 결과, 발생 환경 기록 |
| `PULL_REQUEST_TEMPLATE.md` | PR 생성 | 작업 내용, Scene / Prefab, 에셋, 테스트, 리뷰 내용 정리 |
